🧾 Sign-up, the technical walk-through

The same journey as the simple diagram — but this time with the real Java class names, which method calls which, and the exact data at every hop. Endpoint: POST /api/auth/register
Object born here = a brand-new Java object is created at this step.  ·  Order matters: read top to bottom, that's the exact order objects come to life.
📨
STEP 1 — THE BROWSER SENDS RAW JSON
Your form fields leave as plain text
At this moment there is no Java object yet — just text travelling over the wire. This is the exact body that arrives:
// POST /api/auth/register   Content-Type: application/json
{
  "fullName":   "Asha Rao",
  "email":      "asha@acme.com",
  "username":   "asha",
  "password":   "secret123",
  "department": "Finance"
}
📦
STEP 2 — JACKSON TURNS JSON INTO THE FIRST OBJECT
The JSON becomes a RegisterRequest (the input DTO)
Spring's JSON reader (Jackson) matches each JSON key to a field of the RegisterRequest record and builds it. This is the first object created. A DTO ("Data Transfer Object") is just a typed mailbox for incoming data — nothing more.
RegisterRequest req
What type does each value become? In JSON every value is just text. Jackson reads it into the record's declared types — here, all five are Java String:
// the record IS the type definition — field name : type
record RegisterRequest(
    String fullName,
    String email,
    String username,
    String password,
    String department
) {}

// declared on the controller method:
register(@Valid @RequestBody RegisterRequest req)
🔎
STEP 3 — @Valid CHECKS THE DTO (before any of your code runs)
Are the fields filled and is the email shaped like an email?
The @NotBlank / @Email rules written on RegisterRequest are enforced now, automatically. If anything fails, the controller body is never entered — GlobalExceptionHandler replies for you.
✗ blank field / bad email → 400 Bad Request
🏗️
STEP 4 — THE CONTROLLER BUILDS A User ENTITY
AuthController.register() creates a new User()
The controller copies each field from the DTO onto a fresh User entity — the object that maps to a database row — and stamps the default role. Note: the password is NOT copied here. The raw password stays as a separate string, on its way to the hasher.
Types change here. The Strings from the DTO stay Strings, but two new types appear: the role is a Role enum (not text), and the id will be a Long the database fills in later:
// User entity — field : type
Long   id;           // empty now, DB sets it at save (Step 7)
String fullName; String email; String username;
String passwordHash; // empty now, set by the hasher (Step 6)
String department;
Role   role;         // enum: EMPLOYEE / ADMIN, stored as text
User user 
User user = new User();
user.setFullName(req.fullName());
user.setEmail(req.email());
user.setUsername(req.username());
user.setDepartment(req.department());
user.setRole(Role.EMPLOYEE);   // everyone starts as EMPLOYEE

User saved = userService.registerUser(user, req.password());
🙅
STEP 5 — THE SERVICE ASKS THE DATABASE: "already taken?"
UserService.registerUser() → UserRepository
The controller handed off to the service (business rules live here, not in the controller). The service asks the repository — the object that talks to the DB — two yes/no questions:
repository.existsByUsername(...)repository.existsByEmail(...)
If either is true it throws DuplicateResourceException, which becomes a clean 409.
✗ username/email already exists → 409 Conflict
🔒
STEP 6 — THE PASSWORD IS HASHED (still in the service)
passwordEncoder.encode() scrambles it one-way
Only now is a password put on the User — and it's the bcrypt hash, never the real one. This is why the raw password rode separately: so it could never be accidentally stored.
user.setPasswordHash(passwordEncoder.encode(rawPassword));
// "secret123"  ➜  "$2a$10$k7Q…9fD"   (can't be reversed)
💾
STEP 7 — SAVE, AND GET AN ID BACK
repository.save(user) → row in the users table
JPA runs an INSERT. The database generates the primary key, and save() hands back the same User but now with its id filled in. The service returns this saved user to the controller.
return repository.save(user);  →  User(id=42, …)
🎟️
STEP 8 — THE REFRESH TOKEN OBJECT IS CREATED
RefreshTokenService.create() makes a new RefreshToken()
Back in the controller. A long-lived token (a random UUID) is created, given an expiry, and saved to the DB. This is what lets you stay logged in without re-typing your password.
RefreshToken refresh 
RefreshToken refresh = refreshTokenService.create(saved.getUsername());
// new RefreshToken() → token = random UUID, saved to DB
🔑
STEP 9 — THE ACCESS TOKEN + THE OUTPUT DTO ARE BUILT
authResponse() mints a JWT and packs an AuthResponse
The private helper does three things: (1) jwtUtil.generateToken() creates a signed access token string; (2) it builds a ResponseCookie for the refresh token — HttpOnly, so JavaScript can't read it; (3) it creates the output DTO that will become the JSON reply.
String accessToken (JWT)ResponseCookieAuthResponse 
String access = jwtUtil.generateToken(user.getUsername(), role);
ResponseCookie cookie = cookie(refresh.getToken(), maxAge);
return ResponseEntity.status(201)
    .header(SET_COOKIE, cookie.toString())
    .body(new AuthResponse(access, user.getUsername(), role));
✅
STEP 10 — BACK TO JSON, INTO YOUR HANDS
Jackson turns AuthResponse into the reply
The exact reverse of Step 2: the output DTO is serialized to JSON. Notice the refresh token is NOT in the body — it rides only in the Set-Cookie header. You are registered and already logged in.
201 Created 
// Response headers
Set-Cookie: refreshToken=a1b2-…; HttpOnly; Path=/api/auth

// Response body (from AuthResponse)
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9…",
  "username":    "asha",
  "role":        "EMPLOYEE"
}

Browser → AuthController.register() → UserService.registerUser() → UserRepository (existsBy…, save)
AuthController → RefreshTokenService.create()  ·  AuthController.authResponse() → JwtUtil.generateToken()
