📦 Creating an asset — the two conversions

The outside world speaks DTOs (JSON shapes). The service & database speak entities. The mapper sits in the middle and does two conversions — DTO→entity on the way in, entity→DTO on the way out. Endpoint: POST /api/assets · ADMIN only
⓪ THE WHOLE THING IS ONE LINE — READ IT INSIDE-OUT
mapper.toResponse( service.create( mapper.toEntity(request) ) )
① toEntity DTO→entity  ·  ② create duplicate-check + save  ·  ③ toResponse entity→DTO. Two of those three are the mapper's conversions.
① THE JSON BECOMES AN AssetRequest DTO
📨 THE JSON YOU SENT
{
  "assetTag": "LT-014",
  "name": "Dell Latitude",
  "serialNumber": "SN-9931",
  "status": "AVAILABLE",
  "categoryId": 3,
  "locationId": 7
}
➜
➜
🆕 AssetRequest OBJECT (1st object born)
AssetRequest {
  assetTag     = "LT-014"
  name         = "Dell Latitude"
  serialNumber = "SN-9931"
  status       = AVAILABLE
  categoryId   = 3   ← just a number
  locationId   = 7   ← just a number
}
Jackson builds this DTO from the JSON before your method runs (@Valid checks the fields). Notice: category & location are only ids here — plain numbers.
② THE METHOD LINE — DTO in, DTO out
public AssetResponse create(@Valid @RequestBody AssetRequest request)
OUTPUT = AssetResponse DTO (born last) · INPUT = AssetRequest DTO (born first). The entity never leaves the building — only DTOs cross the wire.
🔧
CONVERSION 1 — AssetRequest (DTO) → Asset (entity) · mapper.toEntity()
DTO → entity, so the service & DB can work with it
Scalar fields copy straight across. But the two id numbers become whole objects — the mapper goes to the DB and fetches the real Category and Location entities (that's why the mapper needs the repositories injected).
asset.setCategory(loadCategory(request.categoryId()));  // findById(3) → Category entity, or 404
asset.setLocation(loadLocation(request.locationId())); // findById(7) → Location entity (null ok)
// id is NOT set — the DB generates it on save
✗ categoryId 3 doesn't exist → 404 "Category not found: 3"
🔎
STEP — SERVICE: REJECT DUPLICATES, THEN SAVE
service.create(asset)
The service only understands entities. It guards the unique fields first: if an asset with this assetTag or serialNumber already exists → reject. Otherwise it saves.
if (repository.existsByAssetTag(...))     throw DuplicateResourceException; // 409
if (repository.existsBySerialNumber(...)) throw DuplicateResourceException; // 409
return repository.save(asset);  // ✅ new → saved, and now it HAS an id
✗ tag/serial already used → 409 Duplicate
🆔
STEP — THE SAVED ENTITY COMES BACK, NOW WITH AN id
Went in with id = null → comes out with id = 14
The database generated the primary key on save. This returned Asset entity is what the service hands back to the controller — richer than what went in.
📤
CONVERSION 2 — Asset (entity) → AssetResponse (DTO) · mapper.toResponse()
entity → DTO, so the client gets clean, richer JSON
A different DTO than the request. It carries the new id, and it flattens each linked object into id + human-readable name — not the bare numbers the client sent.
new AssetResponse(
  asset.getId(),                 // 14  ← brand new
  asset.getAssetTag(), asset.getName(),
  category.getId(), category.getName(),   // 3, "Laptop"  ← name added
  location.getId(), label(location),      // 7, "HQ / 2 / 204"
  asset.getSerialNumber(), asset.getStatus());
🔁 WHY TWO DIFFERENT DTOs?
AssetRequest (in)AssetResponse (out)
id— none (DB makes it)✅ the new id
categorycategoryId onlycategoryId + categoryName
locationlocationId onlylocationId + label (building/floor/room)

🕐 The whole create, start to finish

1 POST /api/assets (ADMIN) with JSON → Jackson builds AssetRequest
2 mapper.toEntity → Asset entity (ids → real Category/Location, or 404)
3 service.create → duplicate assetTag/serial? → 409, else save
4 saved Asset entity comes back — now with a generated id
5 mapper.toResponse → AssetResponse → 201 Created as JSON
